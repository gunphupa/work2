# Running a FixFlow evaluation

Research question: can an adaptive diagnostic system help novice users resolve common Windows computer problems and understand the process?

1. Have a qualified reviewer choose safe, reproducible scenarios and verify the expected causes before a trial. Do not create damage, erase data, induce overheating, or interrupt updates to create test cases.
2. Explain the voluntary feedback and privacy notice. Use participant codes outside the application only if your approved study design requires them; do not put personal information into the app.
3. Record the Windows version and scenario in the study protocol. Choose a fresh tab/session for each trial. Keep the same task and assistance policy across conditions.
4. Let participants follow the app without treating the app's hypotheses as established truth. Use a clear stop rule for discomfort, unsafe symptoms, or a worsening problem.
5. After the session, request optional feedback. Separately verify the actual outcome using the original task. Compare independently verified success with reported success.
6. Export real feedback using the README commands. The submitted-session count is not the number of all visits. Keep synthetic test data out of the study dataset.
7. Report the number of participants, completed and submitted sessions, scenario mix, missing feedback, unresolved cases, limitations, and any assistance given. Duration includes reading and time spent away from the tab, so interpret it as session duration rather than active labor.

For a comparison study, plan scenario balance, randomization/order effects, sample size, and consent with the supervising teacher before collecting results. Do not claim causality from a convenience sample or invent a baseline. The interface contains no pre-populated research results.
